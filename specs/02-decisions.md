# Locked Decisions

Decisions made during scoping. This file is append-only: new decisions are
added, superseded ones are marked, never silently rewritten.

| Decision | Choice | Rationale |
|---|---|---|
| Language | Python 3.11+ | LangGraph ecosystem; user knows Python |
| Orchestration | LangGraph | Conditional confidence gate is a real branch, not a linear chain — the architectural point of the project |
| Graph store | **networkx** (in-memory, persisted to JSON on disk) | Zero setup cost; Neo4j migration is mechanical later because the schema (see [01-system-overview.md](01-system-overview.md) §Graph Schema) is already Neo4j-shaped (roadmap `03-milestones.md` §Deferred #1) |
| Interface | CLI only | Fastest path to signal; web UI deferred |
| LLM provider | Cloud cheap tier behind a thin `judge()`-style interface (exact model: see [03-milestones.md](03-milestones.md) §Open: model pick) | Judgment quality matters at the judge node — small local models are weakest exactly where this pipeline's core novel piece needs them most; a full run costs pennies. The interface makes later local-model benchmarking a config swap |
| Local models | Not for v1 default; later benchmark experiment (see roadmap `03-milestones.md` §Deferred #6) | If the judge produces garbage scores, we couldn't tell whether the architecture or the model was wrong. Benchmark only after the cloud baseline passes the rubric |
| Human-in-the-loop | Simple stdin prompt loop (print low-confidence items → ask → record override) | True LangGraph `interrupt()` + checkpointer adds resumable-runtime complexity a CLI doesn't need yet (roadmap §Deferred #2) |
| Sourcing | LLM project-idea synthesis only | GitHub Issues API is a fragile external dependency (roadmap §Deferred #3) |
| Seed data | Skills JSON + 13 JDs (user-supplied files, in `data/`) | Doubles as the validation set — the project's own test data |
| Spec structure | Modular specs in flat `specs/`, no nested subdirectories | Each spec evolves independently (roadmap `03-milestones.md` §§Deferred/Open churn; decisions is append-only); ~6 files is the right granularity — finer splitting would hurt navigation |
| **(Added M3)** LLM provider | **DeepSeek V4 Flash 0731** via OpenRouter (`deepseek/deepseek-v4-flash-0731`) | 284B MoE / 13B active — strong reasoning/agent capability at flash-tier pricing (~$0.035/M in, ~$0.106/M out); user has an OpenRouter key. GLM + OpenAI remain configured as calibration fallbacks. Supersedes the earlier "GLM 5.3 Flash" interim pick |
| **(Added M2)** Implied-skill handling | Agentic proposal flow, not a static set: detect implications from CV phrases, propose each with evidence, user approves (y/n/a), approvals persist | User identified the static set as a design gap — a CV never states 100% of skills, and only the user can judge "too generous vs. too strict." Evidence-backed proposals keep the human in control |
| **(Added M2)** External taxonomy | ESCO ICT subset as optional enrichment, graceful fallback to built-in tables | Public skill taxonomies exist (ESCO); use where applicable rather than hand-maintaining everything, but never hard-depend on an external file |
| **(Added post-M6)** Specs evolve as one living target-state document; no per-version spec files | All specs describe the full system (current end goal = v2) with Built/Designed status markers; versions are labels on milestone ranges (v1 = M1–M6, v2 = M7+); milestone numbering stays linear and global; `02-decisions.md` stays append-only | User decision after v1 completion: version-split specs (`specs/v2/`) duplicate content and blur which document is current; the unit of change is the component, not the version. Guardrail: never describe not-yet-built things in language that implies they exist (rules in [.github/copilot-instructions.md](../.github/copilot-instructions.md)) |
| **(Added post-M6)** v2 direction: conversational intake + resume ingestion + evidence-backed skill validation | Users hand over a resume (PDF/DOCX) or skills JSON; one LLM extraction call; triaged ranking-relevant skills validated via concept checklist + applied question with hidden rubric; grades persist (`output/proficiency.json`) on the gate's 1–5 depth scale and pre-fill the gate | Resumes inflate and structured skills JSONs are an artifact of the seed pipeline, not real users; evidence-backed depth beats self-report. Design detail in [01-system-overview.md](01-system-overview.md) §M9 design, milestones M7–M9 in [03-milestones.md](03-milestones.md). Framing: calibration, not a test |
| **(Added M7)** LangGraph state does NOT wrap the `SkillGraph` | State is a TypedDict of serializable fields only (paths, flags, stats, decisions); the `SkillGraph` object lives in an in-memory runtime registry keyed by the run's `thread_id`, accessed via the LangGraph `config` | The checkpointer serializes every state channel to disk after every step; a live networkx graph cannot round-trip through that. Supersedes the old §9 design line "a pydantic state object wraps the SkillGraph" — the graph object remains the single source of truth, just beside the state rather than inside it. Detail in S7 [10-flow-runner.md](10-flow-runner.md) |
| **(Added M7)** Judge-recalibration loop deferred | The "re-judge with stricter rubric as a loop" branch is not built; the gate's depth factor compensates for clustered-high judge scores | M6 validation showed ranking already separates true gaps from bridges; an automatic re-judge loop adds graph complexity for an unobserved problem. Revisit trigger in [03-milestones.md](03-milestones.md) §Open: calibration |
| **(Added M8)** Validation metric for resume extraction is "resume content covered", not seed recall | Naive set-recall vs. the seed JSON was rejected: the seed aggregates resume versions + PSE docs + older material, so much of it is absent from any one-page resume (verified by text search). The honest check is whether the resume's actual content lands in the graph, reviewed by inspection + targeted string searches | The user provided their real one-page application CV; a metric that penalizes the extractor for source-material differences measures the wrong thing |
| **(Added M8)** Vocabulary bridge: LLM-assisted merge-or-new for unmatched canonical terms | Canonical terms from new inputs that match nothing in the FULL existing vocabulary (seed canonical + implied + JD lexicon + alias values) get one batched LLM verdict (merge into an existing term vs genuinely new); decisions persist to `output/vocab_bridge.json` and apply silently on re-runs. Manual alias entries remain the first line of defense for recurring variants | The alias table was seed-vocabulary-specific; per-variant manual entries don't scale to arbitrary real-world resumes. The bridge replaces the older "LLM-assisted merge only for ambiguous pairs" idea with a concrete trigger. Merge threshold is conservative (when unsure, keep separate) |
| **(Added M10)** OSS sourcing: unauthenticated GitHub Search Issues for the thin slice; stdlib `urllib`, no new dep | Thin slice runs without `GITHUB_TOKEN` (verified live 2026-09-28); `GITHUB_TOKEN` via the `secrets.py` keyring pattern remains the auth path when set (`Authorization: Bearer`). Network via stdlib `urllib` instead of `requests` — one less dependency for two GET calls | User chose unauthenticated-only for now; rate limits are acceptable for top-5 gaps × ≤2 attempts. `requests` was spec'd as preferred but adds nothing over `urllib` here |
| **(Added M10)** Curated repos as preference re-rank, not hard filter; 2-attempt broaden loop | Attempt 0 strict (label + full keywords + `language:python`); attempt 1 broadened (first token, no language filter) when <3 raw results; results re-ranked to prefer `CURATED_REPOS` | Hard-filtering to curated repos leaves niche gaps (e.g. Data governance) with 0 results, failing the thin-slice done criteria (3–5 issues per top gap). Preference keeps curated signal without starving gaps; the search-and-reason refinement loop is the follow-up |
| **(Added M11)** Local UI: stdlib `http.server` only, no new dep; background thread + status poll; single-run guard; forced `--auto` | `server.py` (`GET /`, `POST /api/run`, `GET /api/status`, `GET /plan.html`, `GET /api/jds`); run = same `cli.py` graph with `auto=True`; 409 while running; options `top_n`/`skip_judge`/`skip_oss`/`no_llm_oss` mirror `cli.py` flags | Same rationale as M10 `urllib` (two GET calls need no framework); judge/synthesis/OSS take minutes so the UI polls instead of blocking; gate/interrupts cannot fire in a browser — `--auto` applies persisted overrides silently |
| **(Added M12)** Evaluation harness: JD-subset sweeps, not a new pipeline stage | `sweep.py` drives the existing `cli.py` graph once per seeded JD subset; per-subset output dirs under `output/sweeps/<sweep-id>/` | The question is whether the *existing* pipeline's plan tracks the JD signal. Re-implementing stages inside the harness would test a different system than the one that ships |
| **(Added M12)** Judge / gate / OSS caches are shared across all subsets; only ingestion, ranking and synthesis are per-subset | `_shared/` holds `judge_report.json`, `gate_overrides.json`, `oss_issues.json`; each `sNN/` holds `graph.json`, `plan.md`, `plan.html`, `synthesis_report.json` | The judge scores target `T` against `prune_candidates(T, sg.current_skills())` — current skills come from the resume, so the score for `T` is subset-independent. Same for gate (asks about the *source* skill) and OSS (query built from `gap.target`). Sharing cuts a sweep from `n_subsets × ~20` judge calls to ~23 total |
| **(Added M12)** Sampling = seeded random `k=3` subsets **plus** contrastive subsets | Random draws for the typical case; contrastive = 3 near-identical JDs, 3 maximally different, all JDs, singletons (`k=1`) | 16 JDs → 560 triples; random draws overlap heavily, so random-only sweeps spend most runs on near-duplicates. Contrastive subsets answer distinct questions (stability under redundancy, fragmentation under diversity) per run |
| **(Added M12)** Manifest records subset membership explicitly, plus a content hash per JD | `manifest.json` lists each subset's JD filenames + hashes, seed, `k`, `n`, model, temperature | `Gap.source_jds` records which JDs *mention* a gap, not which were *in the subset*. Without membership you cannot tell "this JD doesn't need Spark" from "this JD wasn't in the run" — the exact confusion that makes manual inspection useless |
| **(Added M12)** Sweep runs use `temperature=0` and record it in the manifest | `LLMConfig(temperature=0)` for sweeps; the default 0.2 stays for interactive runs | The seed gives *subset* replicability, not *output* replicability. At 0.2 the same subset yields different plans across runs, so a sweep could not be re-inspected or diffed |
| **(Added M12)** Sweep metrics target the review; they do not replace it | Automatic: top-5 Jaccard stability, per-gap appearance rate, superset consistency, rank churn, grounding check, GFI link status. Manual: two-pass (blind score, then reveal subset) | No sealed per-subset ground truth exists (see §Open: sweep ground truth). Automatic metrics say *where* to look; the two-pass review supplies the judgment and avoids confirmation bias |
| **(Added M12)** Seed JD set grew 13 → 16; historical counts preserved | Current-state docs (data-flow diagram, repo map) say 16. Historical records of the M6 validation run (README case study, `03-milestones.md` M1/M2, `08-gap-measurer.md` rubric) keep 13, since that run genuinely used 13 JDs | Rewriting history would make the sealed rubric's numbers (AWS 9/13, RAG 12/13) unverifiable. Supersedes the "Seed data: 13 JDs" row above for current-state purposes only |
| **(Added M13)** Extension UI surface = Chrome **side panel**, not popup or in-page overlay | `chrome.sidePanel`, opens on action click, window-level | User decision 2026-10-03. The popup closes on any click-away — fatal for the capture loop (browse JD → return to panel → capture again). An in-page overlay is destroyed by navigation to the next JD and needs extension-storage state anyway. The side panel stays open across tabs/pages and needs neither |
| **(Added M13)** Two-phase plan generation = one graph run with a pause, not two runs | `phase: "gaps"` runs the `cli.py` graph with `two_phase=True`; a `pause` node after `rank` calls `interrupt()` and the server reports `paused`. `phase: "plan"` resumes via `Command(resume=...)` through synthesize → oss → output | State continuity is free (same `SkillGraph` instance + same `gaps` list); a second run would re-ingest and re-judge or need cache plumbing to avoid it. Reuses the M7 interrupt machinery verbatim |
| **(Added M13)** Captured JDs persist to `output/captured_jds/` as the run's JD set | Same `title\nurl\n\ntext` file shape as the bookmarklet; the folder replaces `data/jds/` as `jds_path` for extension runs | `ingest.py::ingest_jds` reads a folder unchanged — no ingestion changes needed. Keeping extension input in `output/` (gitignored) follows the persisted-artifact convention and leaves the seed `data/jds/` untouched |
| **(Added M13)** Local server sends **no CORS headers**; the extension calls with `host_permissions` | Manifest grants `http://localhost:8000/*` + `http://127.0.0.1:8000/*`; server binds `127.0.0.1`, no `Access-Control-Allow-*`, no `OPTIONS` handler | host_permissions bypass CORS for the extension. Absent CORS headers means a hostile web page cannot read resume-derived gaps (no ACAO) or even trigger a run (JSON Content-Type forces a failed preflight). Trust model unchanged from M11: any *local* process can reach the server |
| **(Added M13)** Extension shell built **before** M9 | M13 scheduled ahead of the still-Designed M9; milestone numbers stay linear | User priority 2026-10-03. The capture → analyze → plan flow runs on the M8 resume path; M9's evidence-backed skill validation improves plan *quality* but is not a mechanical prerequisite for the shell. M9 remains the next milestone |
| **(Added M13)** Gap "highlighting" = gap table in the side panel; in-page JD marking deferred | Panel renders the ranked gap table from `GET /api/gaps`; no DOM marking of the JD page | User decision 2026-10-03. Restore trigger recorded in `03-milestones.md` §Deferred #12 |
| **(Added M13)** Judge cache reuse for extension re-analysis (`reuse_judged`) | Judge node copies `TRANSFERS_TO` edges from `output/graph.json`, judges only still-unmatched targets, merges `judge_report.json` by target. CLI default stays fresh-judging | The judge's score for target `T` is a pure function of `T` (M12 insight), so re-analyzing after adding one JD must not re-pay ~20 LLM calls. The CLI keeps M6's fresh-run validation semantics |
| **(Added M13 fix 2026-10-04)** Plan links open in **new browser tabs**; the plan iframe carries `sandbox="allow-popups allow-popups-to-escape-sandbox"` | `render_plan_html` emits `target='_blank' rel='noopener noreferrer'` on every anchor; `extension/sidepanel.html` sets both sandbox tokens; a **Reopen plan** control re-points the iframe at the on-disk `/plan.html` | User-reported bug: a click on any plan link navigated the sandboxed iframe itself — external GFI links hit GitHub's `X-Frame-Options: deny` ("refused to connect" where the plan had been), the plan view was lost, and "Generate plan" re-runs the LLM phases instead of redrawing. The HTML renderer is the only layer that can set link behavior (the panel cannot reach a cross-origin, script-blocked iframe). `allow-popups` is mandatory — without it `target='_blank'` is silently blocked — and `allow-popups-to-escape-sandbox` keeps the opened tab script-capable; `allow-scripts` stays **off** (plan.html is JS-free) |
| **(Added M13 fix 2026-10-04)** `GET /jds/<name>` resolves from **both** `data/jds/` and `output/captured_jds/` | Exact-name + `.txt`/`.md` match against each folder's listing (traversal guards unchanged) | Extension runs write captured JDs to `output/captured_jds/` and `plan.html`'s JD links are built from that map, but the viewer only served `data/jds/` — every JD link in an extension-generated plan 404'd. Found while fixing the link-navigation bug above |
| **(Added M12, refines the M12 harness row above)** Sweep drives the pipeline stage functions directly (`m5_plan.py`-style), not the `cli.py` LangGraph graph | `sweep.py` calls `ingest_skills_json` + `ingest_jds`, cached judging, `review_targets`, `rank_gaps`, `synthesize_for_gaps`, `source_oss_for_gaps`, `write_plan` with every path explicit | In `--auto` mode (the only mode a sweep runs) the LangGraph wiring adds no conditional behaviour and no interrupts, while its hardcoded `output/` paths would need threading through nodes M11's server also uses. The invariant the earlier row protected — never re-implement a stage — still holds: these are the same functions both existing runners call |
| **(Added M12)** README case study removed; validation evidence lives in the specs | The "Case Study: Validating the Pipeline" section (rubric results table, before/after, sample output) was deleted from README.md; its evidence already exists in `08-gap-measurer.md` §Validation rubric + `03-milestones.md` M6, which stay | User decision 2026-10-03: the write-up was static, stale (its counts predate the 16-JD set and the M8 vocabulary work) and redundant with the specs — and with the M12 sweep as the ongoing monitoring mechanism. The rubric stays: the sweep measures responsiveness/stability, NOT correctness against ground truth (see §Open: sweep ground truth) |
| **(Added M14, Designed)** Observability backend = LangSmith cloud, free Developer tier; not self-hosted | Hosted at smith.langchain.com, nothing to deploy. Self-hosted LangSmith needs an Enterprise licence; Langfuse (open source) is the fallback if a hosted service is ever rejected | Same vendor as LangGraph, so graph nodes trace with no code; free tier covers a single-user dev project. Self-hosting adds ops cost the project has avoided everywhere else (stdlib server, no Docker). Design in [01-system-overview.md](01-system-overview.md) §M14 design |
| **(Added M14, Designed)** Tracing is opt-in, off by default; it never fails a run | Enabled only by `--trace` on the runners or `LANGSMITH_TRACING=true`; `LANGSMITH_API_KEY` resolves via `secrets.py` (env → OS keyring) like every other key, no `.env`; missing key → one warning, run continues untraced | Local-first project: traced prompts carry resume-derived skills and JD text to a third party, so the user must choose it per run. `LANGSMITH_HIDE_INPUTS` / `LANGSMITH_HIDE_OUTPUTS` documented for redacted traces |
| **(Added M14, Designed)** One module owns tracing (`tracing.py`); hooks = wrapped LLM client + stage decorators | `llm._client()` wraps the OpenAI client (`wrap_openai`); stage functions use a `tracing.traced()` decorator that is a no-op when tracing is off or `langsmith` is absent; no other module imports `langsmith` | Mirrors the "LLM access centralized in `llm.py`" guardrail. `llm.py` uses the plain `openai` SDK, so LangGraph's automatic tracing alone would show nodes but not LLM calls; wrapping the one client covers all five LLM callers in one line |
| **(Added M14, Designed)** Judge golden set: committed JSONL of human-agreed confidence **bands**; two metrics | `evals/judge_golden.jsonl` in git (generic skill pairs, no personal data — unlike `data/`); eval calls the real `judge_target()`; metrics `in_band` (judge accuracy) + `pruner_recall` (candidate selection); local report always, LangSmith experiment optional (`--langsmith`); `temperature=0` | Bands, not point scores: humans agree on ranges, not decimals. Two metrics separate "judge scored wrong" from "pruner never showed the right skill" (the M3 LangGraph/AWS miss). The repo file is the versioned truth; LangSmith holds a copy |
| **(Added M14, Designed)** CI split: offline checks on every PR, live eval only with owner secrets | PR workflow runs `ruff` + `pytest` with no secrets/network; live judge eval on `workflow_dispatch` + pushes to `main` touching `judge.py` / `llm.py` / `synthesis.py`; fail on `in_band` drop > 5 points vs. baseline | GitHub does not expose repository secrets to workflows from fork PRs, so a key-dependent eval cannot gate contributor PRs. Offline `mN_check.py`-style stubs keep PR checks meaningful without keys |
| **(Added M14, Designed)** Gate answers become LangSmith feedback as an analysis signal, not judge ground truth | `judge_report.json` stores `trace_run_id`; gate attaches `gate_depth` / `gate_intent` feedback to that judge run when tracing is on; skipped silently otherwise | M4 redesign: the gate asks about the user's depth in the *source* skill and their intent — never whether the transfer score is right — so treating gate answers as judge labels would encode a wrong assumption. Golden-set bands remain the only judge ground truth |
